# Do ISTQB test-design techniques find more bugs than random testing?

A small, fully reproducible experiment. Two systems under test (a shipping-fee calculator and an order state machine) have **known bugs seeded into them** (mutants). Test suites built with different ISTQB techniques are run against every mutant, and the **mutation score** (share of seeded bugs found) is compared with random test suites of the same size.

No network, no browser, only Python: `python run_study.py` reproduces every number below.

## Research questions
1. Which technique (equivalence partitioning, boundary value analysis, decision table, state-transition coverage) finds the most seeded bugs?
2. Does any technique beat random testing of the same size?
3. Which kinds of bugs does each technique miss?

## Method
- `sut/`: specifications and reference implementations. `mutants.py`: 14 + 10 seeded bugs, each a single change to the reference.
- `suites/`: one suite per technique, built mechanically from the specification. Expected values are hand-written, not copied from the code.
- Metric: mutation score = killed mutants / total mutants. A suite kills a mutant if at least one test fails on it.
- Baseline: 1000 random suites of the same size per row (seeded), reporting mean, standard deviation, and how often a random suite did at least as well.
- Integrity checks (`pytest`, 34 tests): every suite passes on the reference implementation, no mutant is equivalent to the reference, and the independent oracle agrees with the reference.

## Run it
```bash
pip install -r requirements.txt
pytest -q
python run_study.py
```
Outputs go to `results/`: `summary.md`, per-system CSVs, `kill_matrix_*.csv` (which suite killed which mutant) and `mutation_scores.png`.

## Interpretation
On the shipping calculator, boundary value analysis was the strongest single technique (10 of 14 bugs, 71%), while equivalence partitioning found only 4 of 14 (29%) and scored below the average random suite of the same size. The kill matrix shows why: equivalence partitioning takes one value from the middle of each class, so it never touches the edges where comparison bugs (for example `<` instead of `<=`) live, and boundary value analysis found all seven such bugs (S01-S05, S07, S08) that it missed. Boundary value analysis in turn missed every bug involving the member discount (S10, S11, S13, S14), because all its tests used non-members; the decision table and full-combination suites caught those, so the techniques complement each other, and the three combined reached 13 of 14 (93%). One bug, S14 (no member discount in the heaviest weight band), survived every suite except full combination, because it only appears when two conditions occur together (a member ordering a heavy parcel). On the order state machine, testing only valid transitions found 2 of 10 bugs, because 8 of the 10 bugs are forbidden transitions that wrongly succeed and those tests never try a forbidden event; testing only invalid transitions found 9 of 10 and missed the one bug where a valid transition was removed (O05); only the full state/event table found all 10. These rankings depend on the bugs I chose to seed (about half of the shipping bugs are boundary bugs), so the result supports "techniques find different kinds of bugs and complement each other", not a universal ranking.

## Threats to validity (keep and extend)
- **I chose the seeded bugs.** About half of the shipping bugs are boundary bugs, which favours boundary value analysis. A different bug set could change the ranking.
- Only two small systems, and one suite per technique. A different tester could build a different equivalence-partitioning suite.
- Suites were built mechanically; real testers mix techniques and use experience.
- The random baseline uses an oracle (a correct reference), as is standard in mutation experiments, but real testers have no perfect oracle.
- Mutation score on seeded bugs is a proxy for finding real bugs.
